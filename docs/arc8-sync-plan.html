Arc 8 — Personal multi-device sync over a self-hosted encrypted relay

Implementation plan. Resolves Arc 8's outstanding design decision in favour of option 4 (encrypted snapshot blobs over the Arc 12 relay), and delivers the Arc 12 §12.3 relay early because personal sync needs it first. One user, three devices, no accounts, no Lacuna-run service that can read anything.

01Scope and recorded decisions

The problem is narrow and it should stay narrow: three devices belonging to one person (a phone and two laptops) currently kept in step by copying BackupFile JSON around, which does not work. Everything below is scoped to that. Tutor receipts, classroom distribution and multi-person merge are out, though the relay built here is deliberately the same relay Arc 12 §12.3 specifies, so receipts inherit it for free later.

Sync mechanism
Arc 8 option 4. Full-state encrypted snapshot, pushed and pulled through a dumb relay, merged on pull. Options 1–3 are closed: option 1 (folder mirror) cannot reach the phone, option 2 (CRDT) is disproportionate for one user, option 3 (local companion process) does not help a phone on mobile data.
Relay hosting
Its own Vercel project, deployed from relay/ in this repo, MIT licensed and independently self-hostable. Not the app's project, so the relay's release cycle is not welded to the UI's.
Merge symmetry
Full symmetric newest-wins on content from day one, even though the phone cannot author yet. See §1.1.
Assets
Inline in the snapshot, as exportDatabase() already produces. Size mitigation in §13.
Trigger
Automatic: pull on app focus, push after a study session ends. Debounced, single-flight, with a visible failure state.
Key transfer
QR pairing and passphrase, both first-class, both yielding the same channel key. Design in §7.

1.1 The phone authoring gap

You want full authoring on the phone but the UI is not at parity yet, which raises the question of what to do in the meantime. The answer is to build the symmetric merge now and change nothing when the UI lands.

The merge is a pure module operating on two BackupFile-shaped snapshots. It has no idea which device produced either one, and it does not care whether a device is capable of authoring, only whether a given record actually changed. A phone that cannot author simply never presents a newer content record, so the content half of the merge is a no-op in practice and becomes live the day Arc 9 ships, with no code change and no migration.

Building a review-only special case would mean an asymmetric protocol, a device-role concept in the payload, and a deletion path for all of it in a few months. That is a parallel system in the sense CLAUDE.md §5 forbids. Skip it.

02Explicitly not building

  • Accounts, identity or authentication of people. A channel id is a capability. Whoever holds it plus the key is you.
  • Any server that can read course content or review history. The relay stores ciphertext and cannot decrypt it, which is what keeps the README's claim structural rather than a promise.
  • Reactivity or subscriptions. Pull on focus is sufficient for three devices that are rarely used simultaneously.
  • CRDTs. Arc 8 option 2 stays closed.
  • Blind last-write-wins on the whole blob. Ruled out in the Arc 8 outline because it discards the losing device's sessions, and still ruled out.
  • A relay Lacuna-the-project operates for other people. You run one instance for yourself. Publishing the code is not the same as running a service.

03Architecture

// Each device, on pull:
   local BackupFile  ─┐
                     ├─> mergeSnapshots() ─> merged ─> importBackup(merged, 'replace')
   remote plaintext ─┘                          │
                                                └─> encrypt ─> PUT (if changed)

// Wire format per channel, stored as two opaque blobs:
   /c/<channelId>/state    AES-GCM ciphertext of the snapshot  // device-written
   /c/<channelId>/keybag   passphrase-wrapped copy of the channel key

Three moving parts. A relay that stores blobs by channel id and knows nothing else. A pure merge module in the app that is the only place sync semantics live. A thin transport behind the RelayProvider seam that Arc 12 §12.3 already specifies, so manual export stays the always-available degraded mode.

Pull-merge-push is the only cycle. A device never pushes without first merging what is already there, which is what makes a lost race harmless (§13.2).

04Blockers found in the current code

Two prerequisites are missing and both must land before any merge code is written. These are the reason this plan has a schema phase at all.

Blocker 1 — most content records have no mutation timestamp

Newest-wins per record needs an updatedAt. Across src/db/types.ts only NoteAnnotation, RevisionPlan and PracticeMilestone carry one. Card, Note, Lesson, CourseRecord, Deck, Sequence, LessonCardLink and CourseAssessment have createdAt at best. Newest-wins is not implementable today on the tables that matter most.

Blocker 2 — deletes cannot be expressed

There are no tombstones anywhere in the schema (nothing matching deletedAt/tombstone/isDeleted). With whole-snapshot newest-wins, a card deleted on the laptop is simply absent from the laptop's snapshot, so the phone's copy wins by existing and the deletion silently reverts on the next sync. Deleted courses resurrect. This is the single most likely way for this feature to look haunted, and it must be fixed in the same migration.

Already correct — review history is a sound event log

sessionHistory is indexed '++id, &eventId, sessionId, deckId, courseId, timestamp', so eventId is unique-constrained, and recordReview in src/db/repository.ts already rejects a duplicate eventId and one belonging to another attempt. Review events are globally unique and idempotently committed, which is exactly the property a set-union merge needs. This was built in schema v16 for undo and happens to be the hard half of sync, done.

05Schema v20 (additive)

Follows the existing convention: additive migration, pre-migration snapshot via preMigrationSnapshots.ts, same shape as v18's purely-additive pass. Arc 6 reserves v19 for occlusions; if Arc 8 lands first, implementation must use the next available schema version rather than leaving a gap.

ChangeDetail
updatedAt: number Added to Deck, Card, CourseRecord, Lesson, Note, LessonCardLink, Sequence, SequenceItem, PracticeNode, CourseAssessment. Backfilled in the upgrade pass from createdAt, or lastReviewed for cards where it is later. Every repository write path sets it; this is the invasive part of the migration and wants a single helper rather than ten scattered Date.now() calls.
tombstones table New: '[table+recordId], deletedAt'. One row per deletion, written inside the same Dexie transaction as the delete itself. Pruned after 90 days, which is the maximum time a device may be offline and still merge correctly. Longer than that and the stale device must be reset from a pull rather than merged.
syncState in appState Channel id, wrapped key material, last pushed generation, last successful sync at, last error. Under the existing appState key-value table, no new table.
BACKUP_VERSION 9 → 10, with tombstones added to the BackupFile payload and to exportDatabase()/validateBackup(). Older backups import unchanged, absent tombstones meaning none.

Decide during implementation

Pre-v16 ReviewLog rows have no eventId and cannot be deduplicated. Proposal: on merge, take local legacy rows as authoritative and never adopt legacy rows from a remote snapshot, so an old row cannot be duplicated by syncing. The alternative, synthesising a deterministic id from cardId + timestamp + grade, is available if you would rather not lose pre-v16 history that exists only on one device. Worth ten minutes before Phase 4.

06The relay service

Its own Vercel project, sources in relay/, deployed independently. Vercel serverless functions plus Vercel Blob for storage. Note that Vercel KV and Vercel Postgres have both been sunset and now route through the Marketplace to Upstash and Neon; Blob is the remaining first-party primitive and is the right one here, since the workload is opaque bytes keyed by a string with a TTL.

EndpointBehaviour
POST /channel Mints a channel: returns a random 128-bit channelId and a bearer writeToken. No body, no identity, no rate-limit story needed for a private instance beyond a global cap.
GET /c/:id/:slot Returns the stored ciphertext for state or keybag, with an ETag carrying the generation number. 404 when empty. Knowledge of the id is the read capability.
PUT /c/:id/:slot Requires the bearer token. Requires If-Match with the generation the client merged from; a mismatch returns 412 and the client re-pulls. Enforces a size cap and refreshes the TTL on write.
DELETE /c/:id Requires the bearer token. Removes both slots. The panic button.

Constraints on the implementation: never log request bodies, never log channel ids, respond with CORS headers (see §13.1), reject anything above the blob cap before reading the body, and keep the whole thing small enough that reading it end to end is a five-minute job for anyone deciding whether to trust it.

07Cryptography

WebCrypto only, no new dependencies (CLAUDE.md §14). One 256-bit random channel key (CK) per channel is the single key that ever encrypts state. QR and passphrase are two ways of obtaining that same CK, never two parallel encryptions of the same data.

CK          = crypto.getRandomValues(32 bytes)          // generated once, on the first device
state blob  = AES-GCM(CK, nonce, JSON(snapshot))       // fresh 96-bit nonce per push, prepended

// QR path: CK travels directly, device to device, never through the relay
QR payload  = { relayUrl, channelId, writeToken, CK }   // scanned once

// Passphrase path: CK is wrapped and the wrapper is stored in the keybag slot
KEK         = PBKDF2-HMAC-SHA-256(passphrase, salt, iterations)
keybag blob = AES-GCM(KEK, nonce, { CK, writeToken })
  • Nonce discipline. A fresh 96-bit random nonce for every single encryption, prepended to the ciphertext. Never derived, never counted, never reused. Two devices pushing concurrently must not be able to produce the same nonce, which random generation gives you and a counter would not.
  • Salt and iterations are stored alongside the keybag in cleartext, which is normal and fine. Pick the iteration count by measuring on the slowest device (the phone) and targeting roughly half a second, then hard-code it with the measurement in a comment.
  • The passphrase is the weak point and the plan should say so. Anyone holding the channel id can fetch the keybag and grind offline. The channel id is a 128-bit random string that is never published, so this is not a realistic remote attack, but a four-word passphrase is still worse than the QR path. The UI should say plainly that the passphrase is the recovery route and QR is the everyday one.
  • No key ever reaches the relay. Not in a URL path, not in a header, not in a query string. The keybag holds the key wrapped, and the wrapping key never leaves the device.

Review gate

This is the one slice where agent-written code with passing tests is not sufficient evidence of correctness, because incorrect nonce or KDF handling produces code that works perfectly and is broken. Run /security-review against this module specifically, and read the diff yourself, before anything is pushed to a real channel.

08Merge algorithm

A pure module, src/sync/mergeSnapshots.ts, taking two BackupFile values and returning a third. No Dexie access, no I/O, fully unit-testable, written and tested before any UI exists, per the convention in the cross-arc notes. It reuses the spirit of importBackup(payload, 'merge') but does not extend it, because that function resolves a foreign import against local state whereas this resolves two peers.

8.1 Order of operations

  1. Tombstones union first. Union both tombstone sets. Any record id appearing in the union is excluded from the result entirely, regardless of what either side holds, unless the surviving record's updatedAt is strictly newer than the deletedAt (an edit after a delete on another device wins, and resurrects deliberately).
  2. Content records: newest-wins per record by updatedAt, with the record id as a deterministic tiebreak when timestamps are equal, so both devices compute the same result independently. Whole-record replacement, no field-level merge.
  3. Review history: set-union on eventId across both sessionHistory and each Card.history[]. Both locations hold review events and must be unioned consistently, or a card's inline history disagrees with the session table and the analytics pages diverge from the scheduler.
  4. Replay to derive FSRS state. Sort the unioned history per card by timestamp, tiebreaking on eventId, and replay through ts-fsrs using that course's trained parameters to produce stability, difficulty, due and state.
  5. Assets: union by hash, which is trivially conflict-free since the hash is the identity. Then re-run the existing referenced-hash sweep so orphans do not accumulate across devices.

Never merge card state directly

Do not take the newer of two Card.stability values, or of due, or of any other scheduler field. Derive all of them by replaying the merged log. Merging them directly produces a card record that looks coherent and that no sequence of reviews could have generated, and once one exists it is undetectable and permanent.

Expected, correct, and surprising

A card reviewed on two devices while both were offline will, after merge, land on a due date neither device predicted, because it now has two reviews in its history rather than one. This is correct. Make sure nothing in the UI treats a due date moving backwards or forwards after a pull as corruption, and consider a one-line note in the sync panel the first time it happens.

8.2 Test coverage this module needs

  • Commutativity: merge(a, b) equals merge(b, a) for every case below. If this ever fails, two devices will oscillate forever.
  • Idempotence: merge(a, merge(a, b)) equals merge(a, b).
  • Same card reviewed on both devices offline, with the replayed state asserted against a hand-computed ts-fsrs result.
  • Delete on A, untouched on B. Delete on A, edited later on B. Edited on both.
  • Pre-v16 legacy rows without eventId, per the §5 decision.
  • A device that has been offline longer than the tombstone retention window.

09Transport seam

RelayProvider, as specified in Arc 12 §12.3, with two implementations from day one: manual (the existing export and import flow, always available, requires no configuration) and http (a relay URL from settings). Sync must degrade to manual with the relay switched off, and the test suite should prove it, because that fallback is what keeps the local-only claim honest rather than aspirational.

interface RelayProvider {
  pull(slot): Promise<{ bytes: Uint8Array; generation: string } | null>;
  push(slot, bytes, ifMatch): Promise<{ generation: string }>;   // throws StaleGeneration on 412
  purge(): Promise<void>;
}

10Orchestration

  • Pull on focus via visibilitychange, debounced so tabbing between windows does not thrash, and skipped entirely if a sync completed within the last couple of minutes.
  • Push after a study session ends, at the same point the session report is produced. Never mid-session: a push during review competes with the write path and risks snapshotting a half-committed session.
  • Single-flight. One sync in progress at a time, per device, enforced with a promise held in a module-level guard. Overlapping cycles are how you get a stale push.
  • Always pull-merge-push, never push alone. On a 412 from the relay, re-pull and retry once, then surface the failure rather than looping.
  • Reuse takeAutoBackup(force) before applying a merged snapshot, so a bad merge is one click from recoverable via the existing restore-point UI. This is the cheapest safety net available and it already exists.
  • Failure is visible but not modal. Last-sync status and last error live in the Settings sync panel. Offline is not an error state and must not present as one, given the app is expected to work with no network at all.

11Pairing UI

A new Settings section, following the existing Settings conventions and the frontend-design skill. No new dependencies: react-qr-code and html5-qrcode are both already in package.json, currently serving the share-code flow.

  • First device: "Set up sync" mints a channel, generates CK, prompts for a recovery passphrase, writes the keybag, pushes the first state blob.
  • Second and third devices: either scan the QR shown on a paired device, or enter the relay URL, channel id and passphrase by hand. Both paths end in the same place.
  • The QR contains the key. Display it only on explicit tap, never on a settings page that could be over a shoulder or in a screen share, and dismiss it on blur.
  • Unpair clears local sync state. Delete channel purges the relay. Distinguish them clearly, since one is per-device and the other is destructive for every device.

13Risks and open questions

13.1 COEP will bite the relay

vercel.json sets Cross-Origin-Embedder-Policy: require-corp on every route, which the FSRS trainer's WASM worker needs. Since the relay is deliberately a separate project on a separate origin, its responses must carry correct CORS headers or the fetch fails in a way that reads as a network fault rather than a policy one. Build the headers in from the first endpoint and add a test that asserts them, rather than discovering this on the phone.

13.2 Concurrent pushes

Two devices merging from generation n and both pushing would let the second silently clobber the first. The If-Match guard turns that into a 412, and because every cycle is pull-merge-push, the loser re-pulls, re-merges (a union, so nothing is lost) and pushes again. Worth an explicit test with two simulated clients, since this is the failure that silently eats a study session.

13.3 Snapshot size with inline assets

You chose inline assets, which is right for correctness and means the blob grows with every image dragged into a note. Set the relay's cap deliberately (start around 25 MB), surface the current snapshot size in the sync panel, and fail the push with a clear message naming the offending courses rather than a generic error. If it becomes a real constraint, the escape is Arc 12's content-hash-addressed asset path, which is why assets are hashed already. Do not pre-build it.

13.4 The updatedAt backfill is where bugs will hide

Every write path in repository.ts must set it. One missed path produces a record that never wins a merge and therefore silently stops propagating, which will present months later as "my notes edit did not reach my phone" and will be miserable to trace. A single write helper plus a test that asserts updatedAt advances after every public mutation is worth the effort here.

13.5 Open

  1. Legacy pre-v16 review rows: drop remote or synthesise ids (§5).
  2. Tombstone retention: 90 days proposed, and what the UI does with a device that exceeds it.
  3. Whether the Electron builds should ship a bundled relay URL default or start unconfigured. Unconfigured is more honest; bundled is less friction for you specifically.

14Success criteria

  1. Three devices converge to the same state after any interleaving of offline edits and reviews, with no manual file copying.
  2. A card reviewed on two devices offline ends with both reviews in its history and an FSRS state derived by replay, verified by hand once on real devices.
  3. A deletion on any device stays deleted everywhere.
  4. With the relay switched off, the app is exactly what it is today, and the test suite proves the manual path still works.
  5. The relay never receives a key, and its stored bytes are indistinguishable from random to anyone holding them.
  6. The merge module's commutativity and idempotence properties hold under test.
