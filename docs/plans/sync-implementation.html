What P3 + P4 buy without a relay

They turn the existing export/import dance into a correct two-device merge. P3 alone is not that merge: importBackup(payload, 'merge') still compares createdAt on most tables. P4 is the merge. September-safe increment is both, in that order, with no hosting.

02Why this, why now

  • Go-live is September 2026. There is no irreplaceable study data yet. Anything that changes how mutations and deletions are recorded is safer now than it will ever be again.
  • The working shape is phone-primary study plus laptop authoring. Three devices, one person. Copying BackupFile JSON around does not keep them in step.
  • Schema v22 just landed. The dual Course/Deck model is gone. Deck and Folder stores no longer exist. Sync work can be written against the target model only.
  • PWA install already shipped. Calibration cannot report before a real corpus exists and stays parked. Arc 14 and the learn-screen redesign are delivered.

03What we are not building yet

  • Accounts, identity, or any Lacuna-hosted service that can read content. A channel id is a capability.
  • CRDTs, live collaboration, folder-mirror, a companion process.
  • A review-only special case for the phone. Symmetric newest-wins from day one.
  • Receipts, reminders, MCP expansion, item-families, calibration.
  • The relay. It is designed in Arc 8. This approval does not stand it up, and does not authorise a Vercel Blob project.

04Architecture reminder

Full design: Arc 8. This section is only the parts P3 and P4 must not contradict.

// Each device, on pull:
   local BackupFile  ─┐
                     ├─> mergeSnapshots() ─> merged ─> importBackup(merged, 'replace')
   remote plaintext ─┘                          │
                                                └─> encrypt ─> PUT (if changed)

Pull-merge-push. Merge is a pure function on two BackupFiles in src/sync/mergeSnapshots.ts. It has no Dexie access and does not know which device produced either snapshot.

  • Tombstones union first. A record id in the union is excluded unless its updatedAt is strictly newer than deletedAt.
  • Content: newest-wins per record by updatedAt, whole-record replacement, id as deterministic tiebreak.
  • Reviews: set-union on eventId across sessionHistory / reviewHistory and Card.history[].
  • Never merge card scheduler fields. Replay the unioned history through ts-fsrs to derive stability, difficulty, due and state.
  • Assets: union by content hash. Existing GC stays as it is.

05Current blockers in the v22 schema

CURRENT_SCHEMA_VERSION is 22 in src/db/schema.ts. BACKUP_VERSION is 9 in src/db/portability.ts. Neither field needed for newest-wins or deletion exists on the tables that matter.

No updatedAt on most content tables

Only NoteAnnotation, RevisionPlan and PracticeMilestone carry updatedAt today. Card, CourseRecord, Lesson, Note, LessonCardLink, LessonCardExposure, LessonCompletion, PracticeNode, CourseAssessment, Sequence, Occlusion, SchedulingUnitRecord, CoursePerformance and SchedulingPerformance have createdAt at best — cards have lastReviewed, scheduling units have lastInteractedAt. importBackup(..., 'merge') already falls back to createdAt for those tables, which is why an edited note never beats its older twin.

No tombstones

Nothing in the schema matches deletedAt / tombstone / isDeleted. A deleted course is simply absent from a snapshot, so the device that still has it wins by existing. Deleted courses resurrect. This is the way the feature looks haunted, and it has to land in the same migration as the timestamps.

Review history is already sound

sessionHistory is indexed '++id, &eventId, sessionId, deckId, courseId, schedulingUnitId, timestamp'. recordReview rejects a duplicate eventId and one belonging to another attempt. Canonical events live in reviewHistory. Nothing in P3 touches either table. Deleting a card cascades into its review events; those deletions follow the card's tombstone rather than getting their own.

7.1 Decisions already taken

One write helper
Every write path stamps updatedAt through a single helper. No scattered Date.now() calls. Defined in slice 2; every later slice imitates it.
Tombstones cover cascades
Every deleted snapshot-carried row gets its own tombstone, including cascaded ones. The merge must not know the ownership graph.
Same transaction
recordTombstone accepts the caller’s existing Dexie transaction. A tombstone written in a different transaction from its delete can survive a rollback and later delete a live record on every other device.
Restore is not an edit
Restore from a snapshot preserves the restored record’s original updatedAt. Stamping it would make an old record beat a newer one on another device.
Undo is not a deletion
Undoing a deletion must remove the tombstones written for that deletion. Leaving them would delete the restored course on every other device at the next sync.
syncState
Lives under the existing appState key-value table: channel id, wrapped key material, last pushed generation, last successful sync, last error. No new table.
90-day prune
Tombstones older than 90 days are dropped. Beyond that a stale device resets from a pull rather than merging. Confirm or change in §12.
Review history
Untouched in P3. Card deletion tombstone covers cascaded review events.
v23 is additive
Still take a pre-migration snapshot via ensurePreMigrationSnapshot. Do not add 23 to DESTRUCTIVE_SCHEMA_VERSIONS (that set is currently {22}). If the upgrade pass throws, Dexie rolls it back and the database stays readable at v22.

7.2 What is snapshot-carried

A tombstone is required only where the deleted row appears in BackupFile as emitted by exportDatabase().

RequiredNot required
cards, courses, lessons, notes, lessonCards, lessonCardExposures, lessonCompletions, practiceNodes, practiceMilestones, courseAssessments, sequences, revisionPlans, occlusions, schedulingUnits, coursePerformance, schedulingPerformance backups (local restore points); appState; in-memory assetCache; undoReview (removes a review event that was never a user-visible deletion); reviewHistory / sessionHistory (follow the card); noteAnnotations (device-local, not in BackupFile); lineageIdMappings / pendingMergeReviews (classroom, not exported); userPerformance (export always emits []); assets (union by hash; GC unchanged)

Replace-import clear() and share-import assessment replacement in src/db/share.ts are not user-visible deletions. They do not write tombstones. Incoming tombstones on a version-10 backup are stored, not applied; applying is P4.

7.3 Helper and transaction rules

Rules every later slice inherits

  • One stamp helper, one recordTombstone helper. Home is src/db/repository.ts or a new src/db/mutationStamp.ts if that reads better. Slices 1 and 2 decide the shape; later slices do not invent a second one.
  • recordTombstone must take the caller’s open Dexie transaction. It must not call db.transaction itself.
  • Every transaction that deletes a snapshot-carried row must list db.tombstones in its table list. Dexie helpers inherit the caller’s complete scope; omitting a table does not always fail loudly under fake-indexeddb.
  • restoreCards, restoreLesson, restoreCourse, restoreSequence and restoreOcclusion put records as they were snapshotted and delete the matching tombstones in the same transaction.
  • stampMissingLessonViewModes is a one-shot display migration, not an edit. It must not advance updatedAt.

08P4 — merge module, sketched not specified

Not fully sliced. Enough to see what comes after P3, not enough to brief a worker. Do not start this until P3 is green.

A pure module, src/sync/mergeSnapshots.ts, taking two BackupFile values and returning a third. No Dexie, no I/O. It does not extend importBackup(payload, 'merge'): that function resolves a foreign import against local state; this resolves two peers. After P4 the two-device dance is merge-then-replace-import. How (or whether) importBackup(..., 'merge') starts calling the new module is part of the slice work, not decided here.

Required properties, from Arc 8 §8:

  • Commutativity: merge(a, b) equals merge(b, a). If this fails, two devices oscillate.
  • Idempotence: merge(a, merge(a, b)) equals merge(a, b).
  • Tombstone-union first, then newest-wins content, then set-union reviews, then FSRS replay. Never take the newer Card.stability / due / state.
  • Same card reviewed on both devices offline, asserted against a hand-computed ts-fsrs result.
  • Delete on A, untouched on B. Delete on A, edited later on B. Edited on both. A device offline longer than the tombstone window.

Open decision, parked here

Pre-v16 ReviewLog rows have no eventId and cannot be deduplicated. Options: drop remote legacy rows, or synthesise a deterministic id from cardId + timestamp + grade. Decide now or with P4 (§12). Not a P3 blocker: P3 does not touch review history.

10Manual testing

Tom tests manually, as usual. After the P3 slices land, walk this in the running app. Automated coverage is named next to each step; the rest is a click pass.

  1. Create a course, a lesson, a note and a card. Edit each once. Automated: slice 3/4 write tests already assert updatedAt advanced. Click: confirm the records exist and edit cleanly.
  2. Export a backup from Settings. Open the JSON. Confirm version is 10, every content record you touched has an updatedAt, and tombstones is an array (empty if you have not deleted anything). Automated: slice 9 round trip. Click: this export.
  3. Delete the course. Export again. Confirm a tombstone for the course, each lesson, each note, each card, each link / exposure / completion, the assessments, sequences, occlusions, scheduling units and performance rows. Confirm there is no tombstone for reviewHistory, sessionHistory, noteAnnotations or assets. Automated: slice 7 cascade test. Click: this second export.
  4. Undo that deletion (the existing undo toast / restore snapshot). Export again. Confirm those tombstones have disappeared and the restored records still carry their original updatedAt, not a fresh stamp. Automated: slice 7 restore test. Click: undo, then this third export.
  5. Import a pre-v10 backup (any current v9 export, or an older fixture). Confirm it still loads. Automated: slice 9 v9 import + legacyCompat.test.ts. Click: one real file through Settings.
  6. If exercisable: force a failed v23 upgrade (the schemaV22.test.ts abort pattern). Confirm the database remains readable at v22. Automated only unless a debug hook is added; do not invent a UI for this.

11Risks

Missed write path

One public mutation that does not go through the helper produces a record that never wins a merge. It will present months later as “my note edit did not reach the phone”. The helper plus one test per public write is the mitigation. Slice 3–5 lists are from the live functions, not from Arc 8’s v20 table list.

Tombstone / delete transaction split

A tombstone committed without its delete, or a delete committed without its tombstone, is silent and permanent once a second device exists. recordTombstone takes the caller’s transaction. Tests must roll a delete back and assert no tombstone remains.

Restore that restamps updatedAt

An undone or restored record that looks “newer” than the live edit on the other device will overwrite it on the next merge. Restore paths put the snapshotted row unchanged.

Undone delete that leaves tombstones

The restored course then dies on every other device at the next sync. Restore must delete the tombstones written for that deletion, in the same transaction as the puts.

90-day prune surprises a stale device

A laptop left closed longer than the window cannot merge; it must reset from a pull. That is the stated contract. Confirm the number in §12. The UI for “this device is too stale” is P6, not P3.

COEP, concurrent-push 412, and snapshot-size risks stay in Arc 8 §13 until the relay is authorised. They are not P3 risks.

13Success for this increment

P3 is done when all of the following are true. P4 is not part of this increment’s success.

  1. Every snapshot-carried write advances updatedAt through the helper.
  2. Every snapshot-carried delete writes a tombstone in the same Dexie transaction, including cascaded rows, including the occlusion cascade deleteCourse is missing today.
  3. Restore and undo put original timestamps back and remove the tombstones for that deletion.
  4. Backups round-trip tombstones at version 10. Older backups still import. legacyCompat.test.ts is unmodified and green.
  5. A failed v23 upgrade leaves the database readable at v22.
  6. The §10 export / delete / undo click pass matches the automated tests.
