Code-quality remediation plan

A bounded maintenance arc to restore a clean quality gate, remove warning noise, strengthen release verification, and extract the two highest-risk architectural seams without changing Lacuna's behaviour. This is not a rewrite and it is not permission to redesign the product while nobody is looking.

01Decision

Proceed. The maintenance work is justified. The codebase has strong behavioural coverage and strict typing, so the risky modules can be improved incrementally. Abandoning or rewriting the project would discard the exact safety net that makes this work tractable.

The work should be completed as a maintenance arc before another broad feature arc begins. Small, already-started feature work may finish first; mixing structural extraction into the current uncommitted occlusion changes would create needless merge risk.

03Scope boundaries

Included

  • Restore a clean lint gate and resolve existing warnings without weakening rules.
  • Remove avoidable stderr noise from the test suite.
  • Add a production web build to CI.
  • Add coverage reporting, then sensible thresholds based on measured baseline.
  • Add a very small critical-path browser smoke suite.
  • Extract persistence domains from repository.ts.
  • Extract pure orchestration and persistence seams from useLearnSession.ts.
  • Update architecture and contributor documentation as each extraction lands.

Explicitly excluded

  • Product features, visual redesign, database schema changes or scheduling changes.
  • A general state-management framework. Adding Redux to make a large hook smaller would be replacing local complexity with ceremonial complexity.
  • Splitting files purely to satisfy a line-count target.
  • Electron packaging in ordinary CI. It is slow and platform-sensitive; a separate release workflow is the correct eventual home.
  • Refactoring every file above 500 lines in one arc.

04Delivery sequence

P0

Freeze and record the baseline

Finish or isolate current occlusion work, record test/type/lint/build results, and list known stderr messages. No code movement occurs in this phase.

git status · package scripts · CI logs · docs/CHANGES.md

P1

Restore trustworthy gates

Fix the TypeScript-project lint failure, remove the eight current warnings, and make bun run lint pass without ignores that conceal production code.

Add bun run build to CI. Keep this phase separate from architectural work so failures have an obvious cause.

ESLint configuration · affected warning sites · .github/workflows/ci.yml

P2

Clean the test signal

Resolve React act(...) warnings in the owning tests, configure router future flags where appropriate, give chart tests deterministic dimensions, add a test doctype, and prevent embed tests from making real network requests.

Do not blanket-suppress console.error. Tests may suppress one expected, asserted message at the narrowest call site.

vitest.setup.ts · affected component tests · router test helpers

P3

Measure coverage before enforcing it

Add Vitest coverage tooling as a development dependency, generate text and HTML reports, and capture the baseline by area. Set initial global thresholds slightly below the measured baseline so CI prevents regression rather than immediately becoming theatre.

Set stronger per-file or per-directory expectations for pure domain logic and database migrations. UI branch coverage may start lower because DOM conditionals are costlier.

package.json · bun.lock · vitest.config.ts · .github/workflows/ci.yml

P4

Extract persistence domains

Move cohesive exports from repository.ts into domain repositories while preserving public signatures and transaction boundaries. Start with low-coupling domains; leave cross-domain course snapshots behind until their dependencies are explicit.

Each extraction is its own commit and passes the full suite. Existing imports may route through a temporary compatibility barrel, removed at the end of the phase.

src/db/repository.ts · new src/db/repositories/*.ts · repository tests · importers

P5

Extract Learn-session seams

First extract pure derivation functions and persistence adapters. Then isolate revision window state and answer/undo transitions if the tests demonstrate a clean boundary. Keep React lifecycle ownership in one hook unless a sub-hook can expose a small, stable contract.

The goal is reduced responsibility, not merely fewer lines. Card selection, grading and persistence must not acquire competing sources of truth.

src/pages/learn/useLearnSession.ts · src/pages/learn/session/*.ts · existing Learn tests

P6

Add critical-path browser verification

Add a small deterministic web suite covering first launch, course creation or seed load, opening a lesson, completing one study interaction, and backup export. Run it against the production build in CI.

Do not reproduce the unit suite in a browser. Five reliable flows beat fifty flaky tours of every button.

browser test configuration · tests/e2e/* · package.json · CI workflow

P7

Close the arc

Remove compatibility barrels, update README.md, docs/SPEC.md and docs/CHANGES.md, then run all gates from a clean checkout.

README.md · docs/SPEC.md · docs/CHANGES.md · CI

Exact boundaries must be confirmed from call graphs before implementation. This table is a target, not an excuse to force functions into the wrong drawer.

Learn-session target boundaries

  • Pure selection input: convert loaded records and request parameters into a session context.
  • Answer transition: calculate the next in-memory state and persistence command from an answer.
  • Persistence adapter: execute review, undo, exposure and revision-plan writes without owning React state.
  • Revision-window state: isolate only if its inputs and outputs can be expressed independently of general card-serving state.

Stop condition: if extraction requires duplicating mutable session state across hooks, stop and retain the existing hook. A long coherent owner is safer than two shorter owners racing each other.

06Testing and commit strategy

  • Every phase begins and ends with type-check, lint and the full Vitest suite.
  • Every extraction commit is behaviour-preserving and independently reversible.
  • Characterisation tests are added before moving logic whose behaviour is not already explicit.
  • Database transaction tests must prove rollback, not merely successful writes.
  • No snapshots are added for complex business behaviour; assert observable records and user-visible outcomes.
  • Incidental bugs discovered during extraction receive separate commits, as required by the project instructions.
  • Coverage thresholds may only rise or remain stable after their initial baseline commit.

07Risks and controls

RiskControl
Repository split breaks transaction atomicityKeep orchestration at a service boundary and test rollback for every moved multi-table operation.
Session extraction changes timing or stale-closure behaviourExtract pure functions first; preserve hook effects and callback dependencies until separately tested.
Coverage work degenerates into chasing a numberPrioritise migrations, destructive operations, merge logic and scheduling invariants.
Browser tests become flakyUse deterministic seeded state, semantic locators and no arbitrary sleeps.
Maintenance arc stalls product work indefinitelyTime-box each phase and permit stopping after P4 if acceptance gates are green and P5 lacks a safe seam.
Active feature edits collide with extractionBegin only after the occlusion working tree is committed or isolated.

08Acceptance criteria

  • bun run typecheck, lint, test and build pass from a clean checkout.
  • The test run emits no unaccounted React, router, chart, KaTeX or network warnings.
  • CI runs the production build, coverage gate and critical browser smoke suite.
  • Coverage thresholds are documented and cannot regress silently.
  • repository.ts no longer owns unrelated CRUD, review, sequence and revision-plan domains.
  • useLearnSession.ts has at least one tested responsibility seam removed, or the phase records concrete evidence that extraction would worsen state ownership.
  • No public behaviour, persisted schema or scheduling result changes.
  • Relevant architecture documentation matches the final module boundaries.
  • No unrelated working-tree changes are included in maintenance commits.

09Approval choices

Recommended approval

Approve P0–P4 now. Reassess P5 after the repository split exposes the true session dependencies. Approve P6–P7 in principle, with browser tooling selected only after checking what the repository already uses at implementation time.

This checkpoint avoids approving a speculative rewrite of the session engine while still authorising the unambiguously useful work: clean gates, quiet tests, measured coverage and persistence boundaries.
