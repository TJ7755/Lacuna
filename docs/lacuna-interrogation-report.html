Codebase interrogation · algorithms, claims, evidence

Lacuna under the microscope

A seventeen-agent audit of the scheduling mathematics, the scientific claims, the data layer, the security surface and the user experience — with every finding labelled by how well it is actually established.

30 July 2026 branch codex/arc6-audio 17 agents · 9 audit · 6 verification · 2 completeness read-only
Fact-checked 9 August 2026

This is a historical audit of the 30 July code state, corrected against the current repository and primary FSRS sources. Its original severity counts are not a current backlog. Claims labelled “verified” by the original audit are not independently reproducible unless the repository retains the script, seed and raw output; unsupported numerical claims are identified in the relevant finding.

Verdict

This codebase is considerably more rigorous than its defect count suggests, and the audit repeatedly failed to break the parts that matter most. The memory model is delegated to the official ts-fsrs rather than hand-rolled. The parameter optimiser uses a chronological train/validation split, an out-of-sample gate and bounds-checked weights — correct methodology that most hobby projects get wrong. The bespoke short-term model was pre-registered, and the pre-registration held: an earlier version failed cross-cohort transfer and was retreated rather than re-justified. Two independent agents, one of them actively attacking, failed to find a cross-site scripting path. The test suite asserts mathematical invariants rather than its own output.

The real defects clustered in three places. The auto-marker converts partial credit into a crude FSRS grade and pools typed-answer production times with ordinary recall latency. Occlusion sharing and documentation were missing in the audited snapshot but have since been implemented. The mature, shipped, user-facing problem remains the analytics: the retention chart shows users a flattering number about their own memory that the data does not support.

Underneath several bugs sits one architectural pattern worth more than any single fix: validation is often enforced in the authoring UI rather than at the storage boundary. It still explains the empty imported mark scheme and weakly validated share payloads. The occlusion orphaning route cited by the original report has since been closed.

The scheduling core

largely vindicated

Lacuna's distinctive bet is that it does not schedule by FSRS intervals. It forward-simulates predicted retrievability to a fixed exam date and picks the card with the largest marginal gain. The audit spent its heaviest effort here and found the mathematics sound.

SoundVerifiedShipped

The memory model is genuinely delegated, not reimplemented

Stability, difficulty, the initial-stability table, mean reversion and same-day handling all come from the installed ts-fsrs@5.4.1, which implements FSRS-6 with 21 weights. Defaults are pulled from the library rather than hardcoded, so the classic mismatched-weight-vector bug cannot occur. The forgetting curve in forwardSim.ts:12-34 correctly implements the FSRS-6 power law and clamps degenerate inputs instead of returning NaN. “Current” here means the installed ts-fsrs release, not the newest FSRS family; FSRS-7 now exists.

SoundVerifiedShipped

The optimiser uses correct methodology

Official fsrs-rs binding, a 1,000-review gate, and — critically — a chronological train/validation split rather than a random one. Random splitting leaks the future in review data; this gets it right. Weights are bounds-checked before application and only adopted if they beat defaults out-of-sample.

CorrectedBenchmarkedShipped

The architecture scales; the name oversells the cost

"Forward simulation" sounds like a day-by-day sweep. It isn't: horizon.ts:34-51 and forwardSim.ts:71-99 project stability analytically via the closed-form power law, so per-card cost is O(1) and card selection is O(cards), not O(cards × days). The original sub-millisecond claim was false: a warmed ten-run fact-check benchmark of scoreCard over 20,000 cards had a 47.2 ms median on the audit machine, before sorting and UI work. The asymptotic claim survives; the performance claim does not.

MediumVerifiedShipped

Elapsed days are computed two different ways

fsrs.ts:62 floors raw milliseconds, but engine.next() discards that field and recomputes internally via dateDiffInDays, which counts UTC calendar-day crossings. Two reviews minutes apart across UTC midnight are one day to ts-fsrs and zero to Lacuna. An unmerged validation branch measured the divergence at max |ΔR| 0.117 (0.022 for elapsed ≥ 1 day) — decision-relevant, not rounding noise. Note get_retrievability uses the same raw-ms formula Lacuna does, so the divergence is isolated to engine.next's scheduling maths.

LowVerifiedShipped

The "single source of truth" invariant is not honoured in revision-plan mode

objective.ts:1-14 and SPEC.md:37 assert that one module guarantees the scheduler and progress display can never disagree. In revision-plan sessions, selection goes through allocateCramReview using the blended half-life model while sessionProgress uses pure FSRS. No user-visible symptom — LearnHeader.tsx:171-172 shows a time-budget bar in that mode and sessionProgress is computed but never rendered. A documentation-accuracy issue, not a bug.

LowVerifiedShipped

DST affects labelling, not scheduling

There is no configurable study-day rollover, so local-day grouping and "due today" buckets shift by an hour when clocks change. Because scheduling elapsed-days ultimately derives from a UTC diff, and UTC has no DST, the interval mathematics is untouched. This is narrower than the source document implied.

LowSingle-sourceShipped

An algorithm-defining dependency floats on a caret range

ts-fsrs is pinned ^5.2.3, resolving to 5.4.1. An install without the lockfile could pick up a minor release with changed default weights. Worth an exact pin given how central it is.

The bespoke short-term model

real science, thin margin

One component is genuinely Lacuna's own invention: a logistic half-life predictor blended with FSRS for short intervals. The original statement that FSRS has “no sub-day memory model” was too absolute: FSRS-6 includes same-day stability handling, but its continuous sub-day retrievability modelling is limited. Anki's tracker has an open PR (#3375) addressing that gap.

SoundVerified via gitShipped

The pre-registration is real, and it bit

ROUTING_DECISION_RULE.md was committed standalone as d02f609 at 12:03:15 on 2026-07-17 and never edited afterwards — no post-hoc threshold adjustment. And the rule had teeth: v1's multi-day advantage won only 1 of 7 lag buckets on both unseen cohorts, so the predeclared rule forced the routing boundary back. A thin win at day 6–7 (n≈300) was discounted as noise rather than banked. That is the opposite of p-hacking.

CaveatVerified via gitShipped

…but the blinding was tighter than "before the results were examined" implies

The reports directory is gitignored, so dating relies on filesystem mtimes. The FSRS-6 comparison file was written 78 seconds after the commit — and since the rule requires both files to agree to call a win, the comparison genuinely could not have been examined first. But the routed model's own result file was on disk 10 seconds before. Verified, but thin: blinded to the comparison, not comfortably blinded to its own numbers.

MediumSingle-sourceShipped

The headline improvement is softer than the number suggests

The reported gap (FSRS-6 2.66 vs 0.39 log loss) is dominated by FSRS-6's whole-day flooring producing near-certain sub-day predictions — a baseline weakness, not a subtle edge. Against the fractional FSRS-6 baseline matching runtime, the advantage in the routed zone shrinks to ≤0.0002 log loss. The team documents this themselves. The one retrospective step in an otherwise pre-registered exercise: the strengthened no-regression gate fails against the floored baseline and passes only against the fractional one, and that reframing came after seeing the failure.

HighVerified ×3Shipped

The spec advertises a model that was tested and rejected

SPEC.md:451 and :1111 describe half-life-logistic-v1 as the model that passed the benchmark and ships as the frozen fit. The runtime loads half-life-logistic-v3-routed. And next_plan.md:756-757 records that v1 explicitly failed transfer validation. The process worked; the documentation did not follow. A fix is already drafted as P7 on an unmerged branch.

The auto-marker

WIP · built the day before this audit

The checker itself is careful work. The wiring into FSRS is not, and the seam is visible: verify.ts uses magnitude-relative epsilon, compares algebra semantically by evaluating both expressions at random points, and keeps an undetermined verdict distinct from different so students are not punished for expressions it cannot evaluate. The grade conversion then reduces partial-credit outcomes to Again unless a currently unwired self-correction path fires.

HighVerifiedWIP

Partial credit is recorded as total failure

grading.ts:92 returns selfCorrected ? 2 : 1 for any partial mark, and both production call sites (useLearnSession.ts:1315, :1377) hard-code selfCorrected false. selfCorrected is dead code — no path in the app sets it true, and the comment at grading.ts:36 describes a feature with no caller. Three marks out of four and zero out of four both write "forgotten" into the memory model. Partial marks are genuinely reachable: WorkingStudyFace sums verdicts across lines.

CorrectedVerifiedWIP

The response timer excludes feedback; the pooled units are the defect

The original finding was false. Machine-marked answers are accepted only in the question phase, and useLearnSession.ts:1308-1310 calculates elapsed time immediately on handler entry, before feedback. Full marks under 3.0 seconds can produce Easy, so machine-marked grades are structurally {1, 3, 4}, not {1, 3}. The genuine defect is that typed-answer production time and ordinary recall latency are folded into the same calibration pool even though they measure different tasks. Hard remains unreachable because both production callers pass selfCorrected false.

MediumVerifiedWIP

An empty mark scheme shows "correct" and records "Again"

WorkingStudyFace.tsx:33 computes correctness as marksEarned === marksAvailable; an empty scheme yields 0 === 0 → green. grading.ts:74-82 treats marksAvailable <= 0 as Again. The authoring editor blocks empty schemes via compileMarkScheme, but the import path never calls it — share.ts:87-125 validates shape with no .min(1), so an imported payload writes one straight through. LearnMode.tsx:507-508 routes on payload kind alone with no length check.

MediumSingle-sourceWIP

Keyword matching has no typo tolerance

verify.ts:260-264 is plain lowercase substring matching. An editDistance implementation exists at markSchemeCompiler.ts:361-396 — but it suggests keywords to the author, never to grade student text. Writing "sub in" against a scheme line reading "substitution" loses that line, and per the finding above, one lost line of four grades the whole answer as forgotten.

LowVerifiedWIP

Dispute reports go nowhere

checkerDisputes is persisted by repository.ts:838 and has zero consumers anywhere in src/ — no review queue, no re-grade surface. A remedy does exist: undoReview (repository.ts:984) fully restores card, calibration and performance state, on a discoverable U shortcut. So a bad grade is fixable, but only until the next answer, and the dispute itself never prompts anyone to look.

LowSingle-sourceWIP

Locale numerals and units are not handled

Unicode minus (U+2212 — what you get pasting from a PDF), decimal commas and thousands separators all fail to parse. In the numeric face this blocks submission; in working lines (verify.ts:266-267) it silently scores zero. No unit handling exists at all, so "1000 m" and "1 km" are not equivalent.

LowSingle-sourceWIP

Editing a scheme silently rewrites history

marksAnalytics.ts:75-114 reattributes historical lineVerdicts to scheme lines by positional index. Reorder or delete a line after reviews exist and past performance is silently misattributed to the wrong criterion. FSRS state is unaffected; the criterion analytics quietly become wrong.

What the app tells users about their memory

the one mature user-facing defect
HighVerifiedShipped

The retention chart is not a retention rate

prepare.ts:184-197 takes each card's single most recent grade and buckets it by now - firstReview. Two compounding defects. First, it collapses every review into one binary sample — a card failed eight times and finally passed reads as 100% recalled — and because FSRS schedules to hit ~90% retention, most recent reviews are passes by construction. Second, age and outcome come from different moments: a card first seen 200 days ago but last reviewed on day 20 sits in the 180+ bucket carrying a 180-day-stale data point.

The sample count is computed (prepare.ts:198-202) and never rendered. A bucket of n=1 looks identical to n=500 and is coloured green at ≥80% (Analytics.tsx:380). The card description reads "Recall rate grouped by how long each card has been in review" — it does not disclose "most recent review only", so the label does not rescue it.

LowSingle-sourceShipped

Forecasts are presented in the register of observations

averagePredictedRetrievability and masteryFraction are model forecasts, not measured pass rates, but UI copy carries no qualifier — unlike retention, which is presented as observed. Both read to a user as facts about their memory.

SoundSingle-sourceShipped

Calibration, streaks and volume charts are honest

calibration.ts:24-56 computes real Brier scores and predicted-versus-actual recall by day. An app that scores its own prediction accuracy and shows you the result is not one hiding from evidence. Streak logic is DST-safe by construction; heatmap and volume series are raw counts with no rate claims to distort.

Data integrity

strong core, weak import path
SoundSingle-sourceShipped

The write path is genuinely well engineered

recordReview (repository.ts:768-948) wraps card update, course timestamps, performance record and session history in one transaction, made idempotent by a unique eventId, and explicitly handles the cross-tab race where a second tab commits the same event first. Migrations run 1→19 monotonically, and ensurePreMigrationSnapshot captures a full snapshot into a separate database before Dexie's destructive upgrade. Opening an old build against a newer database yields a clear VersionError, not silent corruption.

MediumVerified · scopedShipped

On the web build, the safety net lives inside the building it protects

Auto-backups are written via backups.ts:99 into the same Dexie database as the live data, so one eviction or one "clear site data" takes cards, history and every restore point together. The only cross-origin protection is a Chromium-only folder mirror. navigator.storage.persist() is requested at App.tsx:369-379 — right instinct — but Safari grants heuristically and nothing tells the user when it is denied. The Electron build is unaffected: its IndexedDB lives in the app's userData directory, not an evictable browser origin.

MediumVerifiedShipped

Re-importing an .apkg silently doubles the deck

createCards (apkgImport.ts:698) inserts fresh rows unconditionally — no guid, content hash or provenance check. Existing progress is not clobbered, but stats and stability distributions inflate. A checkDuplicatesBatch mechanism already exists (UnifiedImportPanel.tsx:238) and is wired only to the text/markdown path. The capability is built; it just is not connected to the import that most needs it.

MediumSingle-sourceShipped

A study session works from a frozen snapshot

Most of src/state/ uses Dexie useLiveQuery — reactive and cross-tab aware. But a session snapshots db.cards.toArray() once into a plain ref (useLearnSession.ts:1102) and works from it throughout. Two tabs on one deck, or Electron plus a browser tab, and the session serves deleted cards, misses the other tab's FSRS state, and read-modify-writes from stale data. The write path was designed for concurrency; the read path was not.

LowSingle-sourceShipped

Anki scheduling is approximated, and the UI does not say so

apkgImport.ts:525-527 derives FSRS stability from Anki's interval and difficulty from ease factor ÷ 1000. The code comment honestly calls this a "crude approximation for migration"; UnifiedImportPanel.tsx:766-772 tells the user cards arrive "with scheduling history". The code is more honest than the interface. Separately, the import has no wrapping transaction, so a mid-import failure can leave a partial deck.

Security

clean where it counts

Two independent agents examined the untrusted-input surface; the second was instructed to find an exploit rather than assess whether one existed, and to document its failed attempts. Both came back clean on script execution, which is what makes the result meaningful.

SoundVerified ×2Shipped

No XSS path found, including through the suspicious plugin ordering

rehypeKatex and rehypeHighlight run after sanitisation, which is structurally the right thing to suspect. It holds: KaTeX is invoked bare (MarkdownView.tsx:85) so trust is undefined, and \href{javascript:…}, \htmlStyle, \includegraphics all degrade to inert text. Documented failed attacks: SVG/MathML foreignObject smuggling, srcset with javascript:, style-attribute exfiltration, data-* abuse. Electron is hardened correctly — contextIsolation: true, nodeIntegration: false, sandbox: true, a narrow enumerated preload, and a proper traversal guard on the app:// handler.

MediumSingle-sourceShipped

Imported notes are rendered with the trusted-content flag

MarkdownView.tsx:24-29 states in its own comment that allowEmbeds "must only be set for trusted content — do not set this on untrusted or imported content." NoteRow.tsx:150 and AnnotatedNoteContent.tsx:121 set it unconditionally, and mergeImport.ts:126-128 builds notes straight from share payloads with no local-versus-imported distinction. Not script execution — the iframe src regexes are anchored to real YouTube/Vimeo origins — but a stranger's deck can load live cross-origin embeds, violating the code's own written contract.

MediumVerified ×2Shipped

No window-open or navigation handler in Electron

Neither setWindowOpenHandler nor will-navigate is registered in electron/main.ts. If renderer script execution were ever achieved, window.open() would spawn a window with default webPreferences rather than the hardened config. Chained rather than exploitable today, but it is a removed layer of defence.

LowSingle-sourceShipped

Attack markup is reconstituted before storage

convertAnkiHtml() (apkgImport.ts:448-478) decodes HTML entities after its tag-matching regexes, so an encoded <script> slips past every regex and is rebuilt as live markup in the stored card. Blocked at render by rehypeSanitize, so not exploitable — but the database ends up holding attack payloads that rely on one downstream control. Decode before substituting, not after. Separately, no size cap precedes fflate.unzipSync (apkgImport.ts:150), leaving a decompression-bomb DoS; there is no zip-slip risk since nothing is extracted to disk.

SoundSingle-sourceShipped

The MCP surface enforces consent where it should

Grant state and consent gating live in the main process, not the renderer, so a compromised renderer cannot self-grant scope. Scopes are per-course, destructive tools are explicitly gated, and raw FSRS writes, recordReview/undoReview and backup/restore are deliberately excluded from the registry. Residual risk is UX: destructive grants persist for the process lifetime, so one approval covers unlimited deletes until restart. The server starts unconditionally on launch — worth confirming that is intended.

Privacy & deployment

Medium-highVerified · narrowedShipped

"Local-only, serverless" is contradicted on one of two web targets

main.tsx:4,26-34 mounts @vercel/analytics unconditionally — no env gate, no consent, no opt-out. The package resolves to the relative path /_vercel/insights/script.js, which means it does beacon page views on the Vercel deployment and silently 404s on the Cloudflare Workers deployment (wrangler deploy), where it no-ops. Electron's CSP blocks it. So the desktop build is local-only partly by accident of its own header policy. Otherwise the claim holds well: no other outbound calls anywhere in src/ or electron/, no LLM integration, no API keys in repo or bundle. The Electron updater's GitHub Releases check is legitimate but also unmentioned in the README.

MediumVerified · correctedShipped

Security headers exist for Vercel but were never ported to Workers

vercel.json sets COOP, COEP, X-Content-Type-Options and Referrer-Policy. wrangler.jsonc sets nothing at all, with no public/_headers fallback — and wrangler deploy is the target in package.json:26. Neither web target sets a CSP or HSTS, while Electron sets a full CSP. The framing is "config exists but was not carried across", not "no mechanism exists".

Medium-highSingle-sourceShipped

A stale trainer binary can outlive an update

vite.config.ts:49-56 configures CacheFirst for *.wasm with a one-year max age — covering the FSRS trainer. It is runtime-cached by URL regex, not precached with a revision hash, so there is no versioning to invalidate it: new application code can call an old trainer. Compounding this, registerType: 'autoUpdate' with no registerSW call means silent skipWaiting and clientsClaim — the app can reload mid-session with no prompt.

Interface & experience

The core study loop is the strongest part of the product. Errors interpolate real causes rather than generic failures; the no-eligible-cards state explains itself; each answer is written immediately so a crash costs at most the in-flight card; session-end reporting closes the loop legibly. Double-submit is guarded by a ref set before async work and cleared in finally. Large lists virtualise. Dark mode is token-driven. The friction is elsewhere.

HighSingle-sourceShipped

The command palette is invisible to screen readers

CommandPalette.tsx:207-289 tracks the active row in React state and shows it with a CSS class. No role="listbox", no role="option", no aria-selected, no aria-activedescendant. Arrow keys move a visual highlight only, so a screen-reader user pressing Enter activates a result they were never told was selected. For a keyboard-first study app, this is the accessibility defect to fix first.

MediumSingle-sourceShipped

Two unguarded paths to losing work

CardEditor.tsx has no dirty-state tracking, beforeunload listener or navigation blocker — edit a card, navigate away, the edit is gone. And DangerZoneSection.tsx:40-57 deletes a course on click with only a transient undo toast between the user and months of scheduling history. Undo is also single-level throughout (useLearnSession.ts:407 holds one snapshot, not a stack), which matters more than usual here because a wrong grade is a false observation in the memory model.

MediumJudgementShipped

Getting to the core loop takes real authoring work

A new user must create a course, add a lesson, then author or import cards before studying anything. There is no seeded demo inside the app — the demo lives on the separate /welcome page. And LandingCta.tsx:29-38 navigates to / regardless of label, so "Create your first course" simply lands on the dashboard. Course creation itself is admirably minimal: a name, with no forced FSRS decisions.

LowJudgementShipped

Two hierarchies coexist, and an expert knob sits in plain view

"Deck" survives as the legacy global-session unit alongside Course/Lesson (useLearnSession.ts:1098-1103) — consistent with the half-finished migration, but it reads as two competing structures. Separately, requestRetention sits directly in the Study settings tab (CourseSettings.tsx:393-397) rather than behind an advanced toggle: an FSRS-literacy-requiring control shown to everyone. The optimiser, by contrast, is properly gated behind a review-count minimum with an auto-snapshot before applying.

LowSingle-sourceShipped

Smaller items

DateTimePicker has role="dialog" but no focus trap, despite useFocusTrap existing and being used correctly elsewhere — a one-line fix. Only one page-level error boundary exists, so a crash in the occlusion canvas or import panel takes the whole page. And newCardsPerDay <= 0 means unlimited, not zero (eligibility.ts:62-63) — a user typing 0 to mean "none today" gets the opposite.

Tests, process and prior art

The audit discovered mid-flight that prior audits already existed in the repo, and reconciled against them. None contradicts these findings.

  • The test suite is real. forwardSim.test.ts:49-146 asserts mathematical invariants — that forgettingCurve(S,S,decay) ≈ 0.90 across a sweep, monotonic decay, the divide-by-zero guard — not outputs against themselves. objective.test.ts recomputes expectations from a lower-level primitive and explicitly asserts the two objectives disagree, proving the pinning matters. repository.test.ts tests concurrent-replay idempotency against a real database. No tautological or "does not throw" filler in the sampled files. It would catch a scheduling-maths regression.
  • The gap it would miss: nothing exercises the allocator/progress-bar pairing in revision-plan mode.
  • An unmerged validation branch vindicates the scheduler. plan/fsrs-validation sits 25 commits ahead, effectively abandoned in place: TypeScript/Python parity to 1e-14, a cram ablation recommending production routing stay frozen, and a backlog study justifying existing workload defaults. Notably it retracted a prior audit's claim that Lacuna had no review cap — it does. A project that checks its own accusations is a good sign.
  • Prior audits are closed or open-by-design. BROWSER_QA_AUDIT.md found three defects, all fixed and verified. docs/code-quality-remediation-plan.html is an unapproved draft that independently flags the same two oversized files this audit did — repository.ts at 2,686 lines and useLearnSession.ts at 1,802, both well past the project's own ~500-line rule.
  • CI has real gaps. release.yml builds Windows only; ci.yml never builds or tests electron/main.ts, preload.ts or the MCP server, and scripts/mcp-smoke.mjs is not wired in. The privileged Electron surface has no coverage beyond typechecking. electron/updater.ts also has a macOS branch that electron-builder.yml never builds.

Is it backed by science?

literature review · sources cited

A dedicated literature agent assessed the claims on their own terms, without reading the code. The short answer: the foundations are real but the marketing copy outruns them, and the app's most distinctive design decision rests on thinner evidence than its most conventional ones.

SupportedLiterature

The power-law forgetting curve is well-evidenced

Wixted & Ebbesen found power functions fit individual-subject forgetting data better than exponential, linear or logarithmic alternatives. The historical averaging-artifact objection has largely been addressed by within-subject analyses. FSRS cites this literature for its curve choice, correctly.

PartialLiterature

DSR is an engineering approximation, not a validated psychological model

Difficulty, stability and retrievability descend from SuperMemo's heuristics, not from a peer-reviewed cognitive model. They are fitted constructs optimised to minimise log-loss on review logs; nobody has shown they correspond to distinct cognitive or neural quantities. That FSRS beats SM-2 is independently corroborated — Domenech-Iglesias et al. (2024) report ~30% fewer reviews for equivalent retention — but the main benchmark infrastructure is run by FSRS's own organisation, and SuperMemo's creator publicly disputes its methodology, arguing log-loss is the wrong metric and Anki logs are biased toward crammers. That dispute is live and unresolved, not settled.

Partial · discloseLiterature

Exam-date optimisation is plausible, under-tested, and has a real cost the app does not mention

This is Lacuna's defining bet, so it deserves the sharpest reading. It is not cramming — the app reweights which cards get spaced review sooner, rather than collapsing spacing into one session, so Cepeda's meta-analysis (254 studies, 259 of 271 comparisons favouring spacing) does not condemn it. There is prior art in the optimisation literature: Tabibian et al. (PNAS 2019) and Reddy et al. on unbounded human learning. But those are optimisation-theory papers, not randomised trials against standard SRS with real students. The claim "compressing toward the exam improves exam-day recall without meaningfully harming durability" is plausible-but-thinly-evidenced.

The trade-off itself is not speculative. Narrowing the review horizon to a deadline will, by ordinary forgetting-curve mathematics, under-serve post-exam retention relative to an uncapped schedule. That is a predictable consequence, and a user choosing an exam-driven tool deserves to be told it. Separately, "expected marks on exam day" conflates recall probability with exam performance — format effects, question difficulty and transfer are not modelled. A defensible simplification, but not a validated equivalence.

OverclaimsLiteratureShipped

The Help page says more than the evidence supports

"Models your memory with mathematical precision" — overclaim. DSR is a statistical approximation with meaningful per-card error. "The most efficient mode for long-term retention" — unsupported as an absolute; efficiency is benchmark-relative and the benchmark is self-run. "Optimal interval" — true only relative to the FSRS optimiser's own definition of optimal, conditional on the model being correct, and sourced from community analysis rather than peer review.

"Just before you would forget" is the most interesting one. It is roughly what maximising efficiency under a retrievability target implies — but Bjork's desirable-difficulty work suggests the optimal moment for durable learning may be somewhat earlier, where retrieval is more effortful. The phrase elides a real distinction. "Short breaks improve retention" is supported in general, but it is generically true of any study method, not something Lacuna's algorithm does or validates.

PartialLiterature

The retention slider is defensible but under-explained

The 80–97% range matches community consensus that workload is U-shaped in retention target with a minimum around 80–90%. That analysis is SRS-community-authored and simulated under FSRS's own assumptions — somewhat circular. Exposing the control is reasonable; offering the knob without explaining the U-shape invites students to mis-set it.

PartialLiterature

Response-time grading is a reasonable proxy carrying compounding risk

Retrieval latency does index memory strength, and faster initial recall predicts better subsequent retention. But the relationship is noisy, and 3s/8s are engineering heuristics with no validated latency-to-grade mapping behind them. Device, typing friction and anxiety all confound retrieval effort — and because these grades feed a long-term scheduler, an error does not just misjudge one review, it biases every future interval for that card. Note FSRS's own reference implementation deliberately keeps response time out of its scheduling weights. Per-deck self-calibration mitigates this; it does not eliminate it.

OpportunityLiterature

Better-evidenced wins than further parameter tuning

Four effects have stronger and more consistent evidence than several of the app's current claims: interleaving across related topics over blocked practice; elaborated feedback during review rather than correct/incorrect alone; the generation effect, where self-generated answers beat recognition; and successive relearning for weak items rather than purely interval-driven scheduling. Lacuna already blocks during initial teaching and interleaves during practice, which is correct instructional design — the others are open ground.

What this audit got wrong

nine self-corrections

Findings were sent to adversarial verifiers instructed to refute them. Several did not survive, and a report that hides its own misses is worth less than one that shows them.

"No hand-rolled FSRS maths" is not a false claim. Read in full context the README scopes it to memory-state updates, which is true, and SPEC §7 discloses the hand-rolled forgetting curve candidly two sections later. Reading a quoted line in isolation and treating disclosure elsewhere as concealment was the error. Downgraded from "documentation is inaccurate" to a wording nit.

A wrong auto-mark is not permanent. The dispute mechanism genuinely has no consumer, but a working single-step undo fully reverses card, calibration and history state. "Cannot prevent" and "cannot fix" are very different severities and were conflated.

The day-boundary issue is not benign. Initially dismissed as "what Anki does too". An unmerged branch had already quantified the divergence at |ΔR| up to 0.117. This was the audit's own error, not a subagent's.

DST does not affect scheduling arithmetic. Inherited from a source document and repeated before checking. Because elapsed days ultimately derive from a UTC diff, the clock change shifts local-day display and grouping only.

The objective-invariant violation is not user-visible. The claim that a user sees two disagreeing numbers was wrong: in revision-plan mode the header shows a time-budget bar, and sessionProgress is computed but never rendered. Downgraded from medium to low.

The project does have security headers. "No headers anywhere" missed vercel.json entirely, which sets four. The real finding is narrower: they were never ported to wrangler.jsonc.

Telemetry does not fire everywhere. The Vercel script resolves to a relative path that 404s on the Cloudflare deployment, where it silently no-ops. Real on Vercel, inert on Workers.

The backup risk is web-only. Originally rated high. Electron stores IndexedDB in the app's userData directory, not an evictable browser origin, so desktop users are unaffected.

The .apkg importer does not always create a deck. It reuses an existing targetDeckId. The duplication finding survived; the mechanism described was wrong.
